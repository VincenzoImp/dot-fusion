# DotFusion

[![Lint](https://github.com/VincenzoImp/dot-fusion/actions/workflows/lint.yaml/badge.svg)](https://github.com/VincenzoImp/dot-fusion/actions/workflows/lint.yaml)

DotFusion swaps ETH on Ethereum Sepolia for DOT on Polkadot's Paseo Asset Hub
testnet using hash time-locked contracts (HTLCs): an escrow contract on each
chain, locked with the same secret hash. It was built at ETHRome 2025 on top of
Scaffold-ETH 2. It is a hackathon prototype: the contracts have no automated
tests, have not been audited, and have only been deployed to testnets.

## How it works

An ETH to DOT swap through the web app and the resolver runs like this:

1. The app generates a random 32-byte secret (or the user enters one) and
   computes `keccak256(secret)` as the hash lock.
2. The user calls `createSwap` on the Ethereum escrow, locking ETH with a
   12-hour timelock and naming the resolver as the taker.
3. The app asks the resolver API to fulfil the swap. The resolver calls
   `createNativeSwap` on the Polkadot escrow, locking DOT under the same hash
   with a 6-hour timelock and naming the user as the maker.
4. The user calls `completeSwap` on the Polkadot escrow with the secret and
   receives the DOT. The secret is now public on Paseo.
5. The resolver calls `completeSwap` on the Ethereum escrow with that secret and
   receives the ETH.

If either side does not follow through, the party that locked funds calls
`cancelSwap` after its timelock and is refunded. The Paseo timelock is shorter
than the Sepolia one so that the secret has to be revealed while the taker can
still claim on Sepolia. Amounts use a fixed rate of 1 ETH = 100,000 DOT, set in
the frontend and the resolver; there is no price feed.

A third contract, `DotFusionXCMBridge`, is called by the Polkadot escrow on
completion and sends a message through the XCM precompile at
`0x0000000000000000000000000000000000000804`. Its destination and target are
placeholders, so it does not complete the Ethereum side.

The full protocol, every contract function and who may call it are in
[docs/protocol.md](docs/protocol.md).

## Running it

Requirements: Node.js 20.18.3 or later and Yarn (the repository pins Yarn
3.2.3 in `.yarn/releases`).

```bash
yarn install
yarn start          # Next.js app on http://localhost:3000
```

The app targets Sepolia and Paseo (`packages/nextjs/scaffold.config.ts`) and
reads contract addresses from `deployedContracts.ts`, so it can be used against
the testnet deployments below without deploying anything. You need a wallet
with Sepolia ETH and Paseo DOT.

### Resolver

The swap page calls a resolver at `http://localhost:3001` (the address is
hard-coded). The resolver is an Express server that holds a funded key on both
chains and locks the counter-side of each swap.

1. Copy `packages/hardhat/resolver.env.example` to `packages/hardhat/.env` and
   set `RESOLVER_ADDRESS` and `RESOLVER_PRIVATE_KEY`. `SEPOLIA_RPC`, `PASEO_RPC`
   and `RESOLVER_API_PORT` are optional.
2. Copy `packages/nextjs/resolver.env.local.example` to
   `packages/nextjs/.env.local` and set `NEXT_PUBLIC_RESOLVER_ADDRESS` to the
   same address.
3. Start it:

   ```bash
   yarn workspace @se-2/hardhat resolver-api
   ```

Endpoints: `GET /status`, `GET /balance`, `POST /fulfill-eth-to-dot`,
`POST /fulfill-dot-to-eth`. The escrow addresses it uses are hard-coded in
`resolver-api.ts`.

### Local chain and deployment

```bash
yarn chain                      # local Hardhat node
yarn deploy                     # deploy to localhost and regenerate deployedContracts.ts
yarn deploy --network paseo     # deploy to a testnet; needs a deployer account
```

`yarn generate` creates an encrypted deployer key and `yarn account:import`
imports one; `yarn deploy` asks for its password for any network other than
localhost. `ALCHEMY_API_KEY` and `ETHERSCAN_V2_API_KEY` in
`packages/hardhat/.env` are optional (see `.env.example`). To reconfigure the
bridge after a deployment:

```bash
yarn configure-bridge --network paseo
yarn workspace @se-2/hardhat check-bridge --network paseo
```

### Checks

```bash
yarn lint
yarn next:check-types
yarn hardhat:check-types
yarn format
```

The CI workflow (`.github/workflows/lint.yaml`) deploys to a local chain, runs
both linters with zero warnings allowed and type-checks the Next.js app.

## Limits and known gaps

- No automated tests. `yarn test` points at a Hardhat `test` script that does
  not exist, and there is no test directory. `scripts/testXCMBridge.ts` is a
  manual script.
- The resolver does not claim its side automatically. Its event listeners are
  present but disabled in `resolver-api.ts`, so step 5 above has to be done by
  hand.
- In the DOT to ETH direction the app sets the Paseo claimer (`maker`) to the
  user's own destination address, so the resolver cannot claim the DOT. The
  user, who holds the secret, also locks on the chain with the shorter
  timelock, which reverses the safety ordering described above.
- The XCM bridge sends a placeholder payload to a placeholder parachain ID and a
  zero target address. Secret propagation to Ethereum does not work.
- `publicCancelSwap` is meant to be restricted to access-token holders, but the
  check is empty, so anyone can trigger a refund after the timelock.
- `rescueFunds` accepts swaps that were already cancelled and refunded, so the
  owner can withdraw that amount a second time from the contract's pooled
  balance.
- The exchange rate is fixed and not enforced on-chain. Swap history in the app
  lives in the browser's `localStorage`.
- `packages/hardhat/package.json` lists `resolver-service` and
  `resolver-cross-chain` scripts whose source files are not in the repository.
